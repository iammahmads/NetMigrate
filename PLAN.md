# NetMigrate — Full Bob IDE Build Plan (v2, reviewed)

## How to use this plan

Copy each prompt below into Bob IDE **in order**, as separate tasks. Wait for
each task to finish before starting the next.

**Priority order — read this before you start:** Steps 0-6 and 8 are your
**core, required submission**. Get that fully working and deployed first.
Step 7/7a (live upload via Docker + VPS) is a **stretch goal, attempted only
if you have spare time and Bobcoins left after the core is solid and
deployed.** A polished core beats a broken stretch feature every time —
don't let Docker/VPS work eat into core-build time.

**Before you start:** confirm you're on the `ibm-coding-challenge-uat`
(hackathon) Bob account, not your personal one.

**After every task:**

1. Open the Tasks panel → select the task → screenshot the task session
   summary → save to `bob_sessions/` using
   `teamname_taskNN_shortdescription_summary.png`.
2. `git add . && git commit -m "..."` — commit after every completed step,
   not just at the end. If a later step goes badly, you want a clean point
   to roll back to instead of losing earlier working output.

```

   production code.

   artifacts generated by you (Bob) in later steps.

  { "module": string, "purpose": string, "connections": string[],
  "plain_english_summary": string }
- dependency-graph.mmd: Mermaid diagram, nodes labeled with risk_tier as
  "LOW", "MEDIUM", or "HIGH" (uppercase, exact strings)

  [{ "module_name": string, "risk_tier": "LOW"|"MEDIUM"|"HIGH",

  "recommended_replacement": string, "migration_order": number,
  "needs_verification": boolean }] }

  "issue": string, "severity": "low"|"medium"|"high",
  "relevant_standard": string }

Record all of this in AGENTS.md so it persists across all future sessions
and modes. This is a hackathon prototype: prioritize a working end-to-end
```

```
Add a short README.md in /legacy-app explaining this is sample/dummy data
created for a hackathon demo, contains no real credentials, and exists
```

## STEP 7a (OPTIONAL, STRETCH ONLY) — Bob Shell setup for live upload

Do this only after your core (Steps 0-6, 8) is deployed and confirmed
working. This section replaces two earlier draft versions of this setup
that gave conflicting instructions (one recommending an Inference-type
API key, one recommending General) — the guidance below is the single
version to follow.

**Confirmed directly from bob.ibm.com/docs:** Bob Shell has two
authentication methods — IBMid (interactive, browser) and API key
(for automation/CI/CD/non-interactive use — our case). The real CLI
command is `bob` (not `bob-shell`, which was a third-party project's own
naming, not IBM's), invoked non-interactively as `bob -p "your prompt"`.
Non-interactive sessions are **read-only by default** — no separate
sandbox flag is needed, since Bob Shell won't write or modify anything
unless you explicitly pass `--yolo`, and even then it won't write outside
the directory it was started in. This means our "analyze only, don't
modify" requirement is satisfied by default behavior.

**Still needs a final live test, but no longer a guess:** the API key
environment variable name is `BOBSHELL_API_KEY`, confirmed by two
independent sources that both document Bob's own resolution order (env
var checked first, OS keychain second) — not IBM's own docs page stating
it directly, but consistent across independent projects built to mirror
Bob's real CLI. Treat it as reliable, but still verify with one real call
before demo day.

### 0. Confirm outbound firewall access first

A real, documented failure mode: Bob Shell needs outbound HTTPS access to
several specific domains, and a VPS/container with restrictive firewall
rules will fail with `"Failed to login. Message: Authentication timeout"`
with no clearer error — this has happened to someone else exactly this
way. Before anything else, confirm your VPS/Docker host allows outbound
HTTPS to:

```
https://*.us-east.bob.ibm.com
https://api.us-east.bob.ibm.com
https://bob.ibm.com/
iam.cloud.ibm.com
console-ibm-prod.verify.ibm.com
idaas.ice.ibmcloud.com
www.ibm.com
login.ibm.com
myibm.ibm.com
```

(Per Bob's own troubleshooting docs at
bob.ibm.com/docs/ide/troubleshooting/ts-firewall-rules — check that page
directly for the current, complete list before relying on the one above.)

### 1. Generate an API key

- Log in to bob.ibm.com with your hackathon-provisioned account
- Go to API key management under your subscription instance
- Create a **General** key (recommended default — Bob Shell performs more
  than pure inference calls, e.g. orchestration and tool use, which the
  Inference-scoped key type may not cover). If a General key doesn't work
  for some reason, fall back and test an Inference key instead.
- Copy it immediately — it cannot be viewed again after creation

### 2. Check system requirements (confirmed)

- macOS, Linux, or Windows
- 4 GB RAM minimum, 8 GB recommended
- 500 MB disk free minimum, plus headroom for temporary upload extraction
- **Node.js 22.15.0 or later** — check with `node -v` and upgrade first if
  needed; this is stricter than many default VPS/container base images

### 3. Dockerize it

```dockerfile
FROM node:22-slim

# Confirmed install command for Linux/macOS from
# https://bob.ibm.com/docs/shell/getting-started/install-and-setup
RUN curl -fsSL https://bob.ibm.com/download/bobshell.sh | bash

WORKDIR /app
COPY backend/package*.json ./
RUN npm install
COPY backend/ .

COPY docker-entrypoint.sh /usr/local/bin/
RUN chmod +x /usr/local/bin/docker-entrypoint.sh

ENTRYPOINT ["docker-entrypoint.sh"]
CMD ["node", "server.js"]
```

`docker-entrypoint.sh`:

```bash
#!/bin/sh
set -e

# API-key auth is via environment variable, not an interactive login
# command — confirmed pattern per bob.ibm.com's auth method table.
# Verify BOBSHELL_API_KEY is the correct variable name before relying
# on this; set it at `docker run` time, never baked into the image.
: "${BOBSHELL_API_KEY:?BOBSHELL_API_KEY must be set}"

# Accept the license non-interactively on first run (required before
# any non-interactive bob -p call will work)
bob --accept-license -p "Confirm Bob Shell is ready" || { echo "Bob Shell auth/license check failed"; exit 1; }

exec "$@"
```

Run with the key injected at runtime, never baked into the image:

```bash
docker run -e BOBSHELL_API_KEY=your_key_here --restart unless-stopped -p 3000:3000 netmigrate-backend
```

### 4. Isolate untrusted uploads

Since this feature processes code uploaded by strangers, and non-interactive
mode is read-only by default anyway, the main isolation to add yourself is
still the temp-directory-per-request and immediate-delete approach in
Step 7 below — run `bob -p "..."` with its working directory set to that
one temp folder, never the whole container filesystem, and never pass
`--yolo` for this feature since you don't need it to write anything.

### 5. Budget for testing costs

Every call in this section (the license-acceptance check, test analysis
runs) consumes Bobcoins, same as any other Bob Shell use — this is easy
to forget and can quietly eat into the budget you're planning to spend on
Steps 0-6. Do your verification testing with the smallest possible test
file, and keep count.

### 6. Keep it warm

Run the container with a persistent restart policy so the authenticated
state stays available between requests, rather than reinstalling/re-
authenticating per request. Test real end-to-end latency once, with a
realistic small repo, before demo day.

## STEP 7 (OPTIONAL, STRETCH ONLY) — Live upload analysis

**Mode: Code Mode**

```
Add an "Analyze your own code" feature to /dashboard/backend:

1. An upload endpoint accepting a .zip file, max 10MB.
2. On upload: validate that the zip contains only .cs, .csproj, .sln,
   .config, or .json files — reject anything else (especially
   executables) before extracting.
3. Extract to a unique temporary directory per request.
4. Run the same analysis this project already performs (reuse the logic
   /approach from Steps 2-4) against that temp directory, producing
   output in the same schema recorded in AGENTS.md.
5. Return the resulting JSON/Mermaid data to the frontend to render in
   the existing dashboard views.
6. Delete the temporary directory immediately after returning the
   response, success or failure.
7. Add a simple in-memory rate limit (e.g. 3 analyses per IP per hour)
   and a request timeout of 90 seconds, failing gracefully with a clear
   error message if exceeded.
8. Assume Bob Shell is already installed and authenticated inside the
   Docker container (see Step 7a) — shell out to it via
   `bob -p "..."` with the working directory set to that request's temp
   folder (non-interactive mode is read-only by default, so no `--yolo`
   flag is needed here), rather than attempting any login/setup logic in
   the application code.

Do not execute any code from the uploaded zip under any circumstances —
read and analyze only. Add a clear UI note near the upload button:
"Your code is analyzed and immediately deleted — nothing is stored."
```
